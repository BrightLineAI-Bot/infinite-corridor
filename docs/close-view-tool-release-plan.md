# Named tool startup and physical release — architecture for decision

Plan only, 2026-11-08. Source inspected: T `5d76c7ebc4ee19abaf0d2ab984595270eca2ec26`; H constraints read from frozen `b55568365a99906e1c60d007302eaa40400a908d`. No runtime, tests, release identity, assets or other worktrees changed. The previous immediate-release paragraphs in the tool manifest describe that baseline, not the newly approved product direction.

## Approved behavior and proposed choices

The owner approved **accepted press → brief visible startup → physical release; accepted melee may end the remaining body animation after release; tool cooldown remains enforced**. This changes physical emission/contact timing; it cannot be implemented as an additional cosmetic flash over an already flying shot. It does not authorize waiting for the entire 640–840 ms presentation before another action, changing damage, removing cooldown modifiers, or slowing spells.

Recommended implementation: one bounded committed tool-use record, pure phase sampling, and the existing primary input buffer. Keep existing projectile/effect simulation, family producers, area snapshots and pause clock machinery. Do not create a generic action scheduler, animation event engine, recursive pose history or new renderer pass. The first tranche covers Rift Bombard, Blunderbuss, Lumen Spindle and Great Sweep. Hammerfall is an explicit integration constraint, not a second delayed-emission implementation in this T-only tranche.

The owner selected the product behavior; the coordinator has now approved the timing numbers, interruption details and edge-case policies below as implementation defaults. Ordinary implementation and necessary regressions are authorized once this shared API is frozen. No further product question is pending.

| Family | Normal startup to physical release, proposed | Existing cooldown starts at press | Uninterrupted presentation from press |
|---|---:|---|---:|
| Rift Bombard | 120 ms | shared `attackReadyAt`: 360 ms × existing modifiers | 720 ms |
| Blunderbuss | 100 ms | shared `attackReadyAt`: 360 ms × existing modifiers | 640 ms |
| Lumen Spindle | 100 ms | shared `attackReadyAt`: 360 ms × existing modifiers | 760 ms |
| Great Sweep | 160 ms | `toolReadyAt`: 1000 ms × existing modifiers | 840 ms |
| Hammerfall, later H union | existing original-effect 320 ms delay, actual first pulse owns release/contact | existing `toolReadyAt`: 1200 ms × existing modifiers | existing effect-linked 570 ms |

Emitters raise smoothly before the release, then add recoil and their existing useful hold/lowering. Sweep draws back before its release, then crosses the body and recovers within 840 ms. Re-author the analytic stages around these landmarks; merely delaying the shot while retaining recoil at press is wrong. The accepted effective startup duration drives the whole raise/backswing phase, including accelerated variants; the actor reaches its release pose at that duration rather than still sampling a 120 ms cold draw when mechanics release at 32 ms. If a due dispatch is delayed by simulation quantization, hold the release-ready pose until its actual receipt, then start release-relative recoil, without a second clock engine. Same-tool repeats start at the flattened prior pose, use the new startup without a cold draw, and recoil at the new release. Sweep alternates from its existing pose. Do not add startup onto the existing total duration by default; a late receipt must still leave a bounded visible recoil/recovery tail rather than replaying a completed startup.

## Minimal state and acceptance transaction

Add one nullable `Game.pendingToolUse` record, with a strict known version, unique `useId`, recognized family, area/level identity, accepted normalized aim, accepted finite family payload, accepted/release clocks and the original accepted presentation identity. No callback, actor reference, item object reference or renderer state is persisted. The payload is a flat bounded snapshot of values the current producer already computes: base damage/type, motion/path/lifetime/radius, pellet count/spread, applicable passive flags, Echo plan, and required tool/primary configuration for this one release. Preserve recognized unknown extension keys through normalization; never execute an unknown version/family. A tool use is one bundle, not one record per pellet.

Use an additive monotonic schema-14 tool-use counter for IDs, allocated only on acceptance; do not consume generator/drop RNG or re-use wall-clock-only IDs. Base/child IDs derive from that accepted ID with bounded suffixes. This removes same-millisecond collision risk without changing old saved projectile IDs. Do not mint a new accepted identity at release or after reload.

Acceptance order:

1. Check the existing family's enclosure, curse, readiness and admission rules and the new “one unreleased committed use” guard. Refusal changes no accepted record, aim, counters, cost, cooldown or body pose. Do not overwrite a pending use, even if a test or future modifier forces readiness to zero.
2. Resolve and copy accepted identity/aim/config using the current producer. Capture a flattened prior pose only from the latest eligible same-family record; preserve base carry. Consume pending aim only after acceptance. The accepted direction remains fixed even if the player moves or the target turns; aimed Bombard distance/lifetime remains the accepted value, bounded as today.
3. Apply existing costs/cooldown once at press. Keep the current 180/240 ms canonical observation clock anchored at press; it is not the new release guard. Stamp presentation once, now with a versioned use-phase association. New startup records have no base `toolShotId` and cannot produce a muzzle flash yet.
4. Store the pending payload and deadline. No projectile, damaging Sweep effect, child, Echo timer, clone strike, or release-triggered event is created until this use releases. Non-damaging startup belongs to the body pose; no phantom projectile or invisible damaging actor is used as a timer.

Use the accepted snapshot for derived base damage, accepted glyph modifiers, awakened/pellet/passive membership and Echo plan. This prevents changing equipment during startup from replacing an already accepted tool. Existing collision-time glyph callbacks remain collision-time rules unless a focused test proves a required change; do not silently rewrite that broader balance contract.

## Release transaction and simulation ordering

Split each existing producer into “accept/configure” and an internal non-accepting “emit this prepared use” helper. Never implement release by calling public `fireSecondary`/`brawlerTool` again: that would re-check changed gear, charge cooldown twice, re-aim, recurse or stamp a second body action.

On the first eligible active simulation update at/after the deadline, consume the pending record **before** emitting the bundle. Validate owner alive, matching area/level and payload version. Synchronous consume-first dispatch means callbacks cannot execute the same release twice. Do not backdate `releasedAt` to an unobserved theoretical frame: use the actual dispatch `now`, plus an accepted-age-at-release scalar for presentation. Large frame gaps produce one release, never catch-up bursts.

Dispatch after this frame's ordinary player movement and before ordinary primary acceptance, while accounting for the existing earlier tool/dodge/form input paths. Thus emission uses current canonical player coordinates at release and accepted aim. Base gun origin remains the existing `.35` forward offset from `.5/.45` center; **do not move canonical origin to an imported socket**. Movement during startup is allowed. Use normal collision at the resulting position, including point-blank walls/targets; never jump a shot forward to make it reach the model muzzle.

Newly dispatched shots must not receive the entire already elapsed frame's `dt`. Add a narrowly scoped frame-local newborn set/step override to the existing projectile step: new bundle members receive zero elapsed motion/lifetime on that dispatch frame, but still perform zero-distance canonical collision checks. Subsequent frames use the normal path. Do not persist a duplicate birth timer, pre-integrate a shot without collision, or change older shots' step. Test point-blank grenade detonation, ordinary collision and Spindle reflection with this path. If implementation instead chooses residual-time stepping, it must define and test a real subframe movement origin; current-position plus retroactive full-frame travel is unacceptable.

Sweep creates its ordinary damaging effect at the player's release-time center, then keeps that fixed center exactly as the current area effect does. It does not become a follow-player aura. Retain Shadow Boxing's existing acceptance-time step; do not dash twice at release. Stamp physical release only once the effect is created and admitted to its first normal effect pulse. It is valid for damage to be quantized to this update; no second `.16` effect delay is added on top of the pending startup. Re-evaluate the short phase against actual release so the body cannot complete its strike before a late dispatch.

All simultaneous base pellets/fans and the shot event are created at release; existing child offsets, damage shares and hit maps remain independent. Queue tool Echo relative to **actual parent release**, not press. Clone eligibility/position/aim uses the existing live clone at release; the accepted tool payload supplies its shot content. A vanished clone does not leave a reserved phantom copy. Neither children nor later Echo replace the body, extend its hold, or own its current-hand flash. Preserve the bounded family expansion and existing admission/draw caps; no new live actor kind or extra draw pass.

After dispatch, retain a small release receipt on the *matching* accepted visual record (`useId`, actual release offset and base source ID). Never attach it to a newer unrelated record. Absolute runtime release time, if retained for callbacks, participates in pause shifts; serialized presentation uses finite elapsed/remaining values. The renderer derives age from logical accepted age minus actual release offset, and requires an explicit released receipt for new records. Existing records without the new phase version retain their old immediate-age behavior and are never physically replayed.

## Melee weaving and other interruptions

All **non-Echo** primary entry routes, including direct calls, tap, buffer, Fist charge start and Fist punch release, must check the unreleased-use guard before replacing presentation or dealing new melee damage. Delayed already accepted primary Echo bypasses the body guard and retains its own mechanics. Do not block an unrelated existing physical effect merely because a startup body is visible.

Recommended startup input handling: reuse the existing 120 ms intent window, adding a narrowly scoped startup-deferred path for Fists without enabling a general Fist buffer everywhere. A press can wait only when its earliest legal start is within that window; otherwise it is refused and must be pressed again. Earliest blade start is `max(actual tool release, current attackReadyAt)`, and earliest Fist start is actual release plus its existing charge/recovery rules. Recheck readiness at dispatch; never subtract tool startup from primary cooldown, emit two primaries to catch up, or turn an old tap into indefinite auto-attack. Repeated pending taps replace one intent, not a list. A held Fist starts charging when it legally begins, not retroactively at the blocked input; a released tap uses the existing uncharged path. Pause, death, area transition and invalid primary context clear intent, matching the existing buffer's non-persistent behavior.

After physical release, an accepted primary immediately replaces the remaining tool body; a refusal does nothing. All live shots, Sweep effects, future Echo and tool cooldown continue. Fists retain their independent readiness rather than inheriting blade readiness. A buffered primary may begin on the release update after the release transaction, but the earlier startup was still real. The current final-selected-action cue rule may suppress the flash when melee owns that same rendered frame; do not borrow the new melee hand or force a second body pose to display a flash.

Recommended other interruption policy: ordinary hit flash, dodge, jump, cast, knockdown, equipment/active-slot change and visual form changes may win the existing body priority, but **do not undo an already committed physical use**. Its release still uses the accepted payload at the current valid owner position; recovery must not revive an older body under a newer action. Death, fatal travel/area transition or explicit world reset discard an unreleased use without refund/replay. Cooldown remains spent. Same-area equipment change is not a refund exploit. Resolve death before dispatch. A successful teleport to another area cannot carry a delayed shell into that area; bind the pending record to the actual area/level identity and clear it before outgoing snapshots can resurrect it. Same-area ordinary movement/knockback is allowed. This is a committed-use recommendation, not a claim that the owner explicitly specified every interruption.

## Hammerfall integration boundary

Keep its accepted target, `.32` delay, original ID, 254-triangle native body, connected imported feet/arms, ordinary carry under empty gear and 570 ms effect-linked presentation. Do not wrap H in the emitter's pending delay, move its target to the player's release center, or add another 320 ms. Its effect is an authoritative pending adapter: unreleased while `delay > 0` **or** `pulseIndex` has not advanced, released at the original first pulse. Echo/clone/golem IDs cannot satisfy that predicate.

Because `updateEffects` crosses zero on one update and pulses on the next, H's legal melee release point must follow the actual original pulse, not `press+320` alone. A narrowly scoped post-effects buffer check may admit a waiting primary in that same pulse update; do not reorder all primary/monster simulation. Missing/dead original effects end the association without firing another effect. H cleanup/death/snapshot semantics remain authoritative. When H is actually integrated, all its 30/60/uneven-frame, remote impact, pause/JSON and entry/recovery carry regressions must pass against this guard. This document does not authorize editing frozen H now.

## Pause, save, old records and fallback

Put pending-use normalization in the established pure runtime/action-data layer, restore only after the correct area and player state are loaded, and include it in both runtime export paths. `shiftClocks` must cover its accepted/release stamps, or derive them consistently from a single shifted start; do not shift both a derived duration and a deadline. Serialize remaining release time, accepted elapsed time, area key, bounded payload and identity. Zero remaining is a valid due-but-not-yet-dispatched use and releases once on the first active update after load; released/cancelled records cannot become pending again. Paused saves use the pause clock and do not release merely because a render/export sees a later wall clock. The pending use survives pause; buffered player intent does not.

Old snapshots lacking this field retain their immediate projectiles/effects and existing motion versions. Never infer pending mechanics from a visual record, an old `toolShotId`, equipment, or a `.32` delayed effect unless it is the explicitly recognized H adapter. Unknown pending versions remain opaque/inert, preserve extension fields on round trip, reserve no active slot, and cause no cooldown or emission. Malformed recognized fields discard only the executable pending state, not unrelated schema-14/world/unknown data. New motion-version sampling must preserve old v1 behavior; current `toolMotion` normalization rejects unknown versions, so do not claim that a new future-version test already passes—explicitly correct/cover that compatibility boundary during implementation.

The physical transaction applies equally with GL disabled, assets missing, native forms and reduced motion; presentation readiness never delays/releases a projectile. Use existing native/tool fallback startup poses where available. Reduced motion keeps the mechanical delay and a restrained readable ready/release cue; it does not make shots immediate. Imported release cues stay on the actual current socket only when that tool still owns the final action. Retain the generic GL transaction, floor fallback ownership, budgets, discovery/wall bounds, canonical projectile head and exclusive draw ownership.

## Coordinator-approved edge policies

1. **Accelerated and zero cooldowns.** Scale startup down with the *accepted effective cooldown ratio*, capped at the normal startup above; keep the actual cooldown deadline beginning at press. Ordinary cadence is unchanged, including three Swift glyphs plus armor, which can make emitter readiness shorter than 100/120 ms. Positive scaled startup must never be rounded to zero. There is no way to promise a visible nonzero windup, unlimited same-timestamp accepts, and only one bounded pending use simultaneously. The approved 1 ms minimum startup and refusal while the one use remains pending for nonpositive/sub-millisecond cooldowns explicitly create a one-update minimum at that extreme. Do not hide that tradeoff or impose a 720 ms gate. Later Wellspring reductions change readiness normally but cannot retroactively erase an already accepted startup.
2. **Capacity fills during startup.** Existing cap admission occurs before immediate creation, and children already use family-specific expansion. A new delay introduces a race with other projectile producers. Repeat the unchanged base admission check at release; if it no longer fits, terminally cancel this unreleased bundle, retain the spent cooldown and clear its body association, with no late replay. This new rare failure condition is explicitly coordinator-approved. Do not add global reservations, increase caps, silently stall indefinitely or evict unrelated shots.
3. **Melee/interrupt policy.** Recommend the finite existing 120 ms buffer and committed-use policies above. They preserve blade/Fist readiness rather than making every early tap queue indefinitely or allowing a successful pre-release melee to erase the use. If the intended experience is instead “every startup tap executes at release even when normal primary readiness is later,” that changes primary cadence and is a separate product choice. The current recommendation does not do that.

## Frozen shared API and ownership (coordinator-approved defaults)

This section takes precedence over informal field-name examples earlier in the plan. It is the handoff boundary for two nonoverlapping workers. Runtime owns `game.ts`, `types.ts`, `action-motion.ts` and its physical/normalization tests. Presentation owns `close-view-hero.ts`, `close-view.ts`, `close-view-models.ts` only if necessary, and its renderer/pose tests. Runtime must not edit presentation files; presentation must not edit the shared pure module. Communicate a concrete contract defect before changing these names. No H/S/A files are owned by either tranche.

### Eligibility and top-down preservation

Runtime extracts/exports `closeViewActionEligible(game)` from the **geographic/view portion** of `closeViewAttackBufferEligible`: `save.closeView === true`, dungeon interior, non-finale building; the existing bounded landscape/interior, stillworks/cloud/mover/canopy exclusions; no courtyard/open-air/roof/balcony/yard tile under the player; live player. It reads game/map data only and must not call a renderer, inspect GPU/assets, or mutate a notice. Existing primary-buffer eligibility then adds its current Fist, active-slot, attack-curse and enclosure restrictions. Do not copy those weapon-specific restrictions into tool-startup eligibility, or tools equipped in the secondary slot and players wielding Fists would silently skip startup. Existing tool producers retain their own refusal checks.

Only a **new accepted** recognized use with `closeViewActionEligible(game) === true` receives delayed mechanics. All new ordinary top-down/overworld/ineligible uses retain the exact old immediate producer path and old visual metadata. There is no cross-mode cooldown rebalance. Once accepted, a pending use retains its startup even if Close View is disabled or the player walks onto an open-air tile; its mode decision is latched. Missing imported assets, native forms, reduced motion and GL fallback never change eligibility. Area/level transition remains the cancellation boundary.

### Data shapes

Plain JSON fields, no classes/functions/renderer references. All times below are milliseconds.

```ts

  id: string;                    // unique accepted-use identity, <=160 chars
```

`PreparedToolPayloadV1` is a runtime-owned schema, opaque to presentation. Its top-level fields are `v:1`, `family:'shot'|'sweep'`, `shot` (prepared base shot data) or `effect` (prepared Sweep data), `pellets`, `spread`, `awakenedFan`, `echoCopies` (bounded `{delayMs,share}` entries), `cloneEligible`, and `cloneProfile` where a Sweep clone needs the accepted primary profile. Shot/effect objects contain only finite validated values/booleans/known enum strings needed by existing producers; omit position, age, life-consumed state, hit maps, mutable actor references and IDs until emission. The prepared base lifetime is retained as a payload value. Apply the existing family's passive modifications before storing these values. `cloneEligible` freezes accepted permission/configuration; actual live clone presence/position/aim is checked at release. The runtime worker owns exhaustive bounds for this schema and tests all existing descendants; no presentation worker may interpret it or add fields to make a visual work. Preserve unknown extension keys without executing them.

`save.toolUseCounter` is an additive nonnegative safe-integer counter, incremented once per accepted delayed use, preserved on migration/export. IDs use `tool-use-<counter>` plus fixed child suffixes; include an existing stable journey identity if needed to avoid crossing saved journeys, without RNG. Counter exhaustion/nonfinite input must fail closed for new delayed acceptance rather than wrap to an existing live ID. Legacy projectile IDs remain unchanged. `toolUse.id` and pending `id` must match before resolving pending presentation or attaching release metadata.

### Pure exports from action-motion.ts

```ts
export const TOOL_USE_STARTUP_MS = Object.freeze({
  'rift-bombard':120, blunderbuss:100, 'lumen-spindle':100, 'great-sweep':160
});
export function toolUseStartupMs(kind, effectiveCooldownMs): number | null;
export function normalizeToolUseVisual(raw, toolKind, durationMs): object | null;
export function normalizePendingToolUse(raw): object | null; // SAVED relative-time shape
export function toolUsePoseTime(record, elapsedMs): {
  phase: 'legacy'|'startup'|'released'|'cancelled'|'unknown',
  elapsedMs: number, startupMs: number, releaseAgeMs: number | null
};
export function toolUseReleaseAge(record, elapsedMs): number | null;
```

`toolUseStartupMs` returns `max(1, normalStartup * clamp(effectiveCooldownMs/baseCooldownMs, 0, 1))`, using base 360 for emitters and 1000 for Sweep; unknown kind/nonfinite cooldown returns null (refuse new delayed acceptance). Keep fractional positive milliseconds; do not round to an update tick. An ordinary legitimate zero/negative effective cooldown takes the approved 1 ms floor. Store the result once at acceptance; subsequent equipment/modifier/Wellspring changes cannot recompute it.

`normalizeToolUseVisual` validates recognized v1: exact family, finite bounded duration, startup range, phase enum; released requires finite `releaseOffsetMs === startupMs`; startup/cancelled must not carry a release offset. Return a copied record with unknown extension keys preserved. Unknown positive-integer versions return an opaque shallow copy and are never interpreted as v1. Malformed known v1 returns null. `normalizeAttackVisual` uses this helper: missing `toolUse` preserves legacy; invalid known `toolUse` removes only that optional association and cancels its new-use cue eligibility, **never downgrades a corrupted new use into a legacy immediate flash**. Implement that via a retained inert `toolUse:{v:1,id:<valid-id-or-'invalid-tool-use'>,phase:'cancelled',startupMs:<bounded-or-1>}` marker; it is presentation-only and cannot create pending mechanics. Unknown version stays opaque and suppresses new-use cues. A malformed `toolMotion` is likewise not a reason to recreate a physical use.

`normalizePendingToolUse` accepts only the relative-time saved shape; known v1 validates family/id/area keys, aim, payload, `startupMs`, `elapsedMs` in `[0,startupMs]`, `remainingMs` in `[0,startupMs]`, and their sum equal to startup within numeric tolerance. Preserve zero remaining. It copies nested recognized data/unknown fields without retaining runtime references. Unknown positive-integer versions are copied opaquely into save state but never installed as executable `Game.pendingToolUse`; they reserve no slot. Malformed recognized pending state becomes null independently of other save fields. Runtime live records are created/restored from normalized saved data, not passed through the saved normalizer with absolute clocks.

`toolUsePoseTime(record, elapsedMs)` clamps finite input to `[0, record.durationMs]` and returns deterministic data. Missing `toolUse` yields `legacy` and unchanged elapsed. Recognized startup clamps elapsed to `startupMs` and has null release age; released has `releaseAgeMs=max(0,elapsedMs-releaseOffsetMs)` and cannot be sampled before startup; cancelled/unknown are inert with null release age. `toolUseReleaseAge` returns this release age for released v1, unchanged bounded elapsed for absent legacy association, and null for startup/cancelled/unknown/malformed. These functions consume no Game state, time source, assets or RNG.

`sampleToolActionMotion(record, elapsedMs)` retains its existing signature and result `{yaw,side,up,forward,weight}`. Runtime extends it using `toolUsePoseTime`: v1 `toolMotion` **without** toolUse keeps byte-equivalent old motion; recognized startup maps its effective startup duration onto the authored raise/backswing with no recoil; recognized released uses release-relative recoil and the existing hold/recovery deadline. The first instant remains the flattened entry exactly. An opaque future toolUse/toolMotion is never interpreted as known mechanics; neutral/current carry is the fallback. Modify current toolMotion normalization to preserve opaque future versions rather than rejecting the entire accepted record; all consumers must keep their existing `v===1` guard. No new motion version is needed for this tranche because toolUse selects the new phase semantics explicitly.

### Runtime clocks, late dispatch and presentation deadline

Freeze `attackVisualDeadline(player, record, context)`'s optional context extension to `{ now, effects?, pendingToolUse? }`; its old two-argument behavior remains unchanged. With matching valid startup association/pending identity, compute `poseAge=clamp(now-pending.acceptedAt,0,startupMs)` and return `now + record.durationMs - poseAge`. This holds the ready pose indefinitely if the simulation has not dispatched yet, **without increasing durationMs or serializing huge elapsed ages**. A mismatched/unknown pending record cannot hold an unrelated body. Preserve H's existing effect-aware branch when merged; do not implement that branch from scratch on T.

At actual release, only if the current accepted record still matches the pending use ID, remains in startup, and is not presentationCancelled, set `toolUse.phase='released'`, `releaseOffsetMs=startupMs`, attach base `toolShotId` if any, and set `player.actionVisualUntil = actualDispatchNow + (durationMs-startupMs)`. Do not re-stamp a new accepted action or overwrite a newer unrelated body's clocks. This deliberately rebases only the presentation clock: its displayed age is startupMs on dispatch even if the wall-clock gap was ten minutes. A full bounded follow-through tail remains. There is no persisted raw actual-release absolute timestamp; this deadline plus the release offset is the receipt clock, shifted by existing pause handling. If the old body was cancelled/overridden, physical release still occurs, but that body is not revived and receives no newly extended deadline. Native/2D paths use the same actual physical event.

`closeViewPlayerAction` passes matching `g.pendingToolUse` in the deadline context. Both runtime save writers use that same contextual deadline. Pending save conversion uses `remainingMs=clamp(releaseAt-clock,0,startupMs)` and `elapsedMs=startupMs-remainingMs`, where clock is pausedAt while paused. Restore `acceptedAt=now-elapsedMs`, `releaseAt=now+remainingMs` after area validation. Add those two absolute fields to `GAME_NESTED_CLOCKS.pendingToolUse`; shift each once. Ordinary `actionVisualUntil` already shifts once. After release, existing remaining presentation normalization suffices; duration remains the family's value, well below the existing 5000 ms bound. A due-but-unreleased save remains startup, not an invented released receipt. New acceptance without a valid pending record must not leave a stuck startup visual.

Presentation consumes the record/elapsed helper only. Do not subtract startup independently in the renderer or reset a renderer-owned timer. Recoil and release cue share the same rebased timeline. ### Runtime release/guard entry points and newborn stepping

Runtime methods: `releasePendingToolUse(now)` returns `{ released:boolean, cancelled:boolean }`; `cancelPendingToolUse(reason)` terminally clears one pending association and marks only its matching visual `toolUse.phase=cancelled` plus `presentationCancelled=true`; `toolUseBlocksPrimary()` is true only for a recognized live pending use (later H adds the original-effect adapter). None depends on rendering. Due draining is idempotent and consume-first. Call the due-drain before direct tool/primary entry so a due prior use is not overwritten or kept artificially pending by an input-only caller. That drain is the prior use's work, not acceptance side effects of a refused new press. Never drain paused/dead/mismatched-area uses as a physical release. Fists' direct press/punch routes receive the same guard before their existing readiness/charge logic. Release of a pre-existing unrelated Fist charge may wait/refuse under the same finite intent policy; it must not secretly deal damage before the tool releases.

In `update`, drain after player movement and before primary-buffer/input acceptance. The newborn collection is **frame-local**, contains identities/references of the directly emitted base/pellet/fan/clone shots and directly emitted Sweep effects, and is passed to the existing stepping path rather than persisted in a second clock. Outside-update direct draining must retain one bounded “not stepped yet” marker until the next update; consume it once. This can live on the newborn objects as a recognized boolean `toolUseNewborn:true` that snapshots preserve until their first simulation step. It is not a time source. The runtime worker may use this single marker for both direct and in-update paths instead of a Set; do not implement both competing systems.

For a recognized newborn shot, the first `updateProjectiles` invocation uses per-object elapsed **zero** for age, movement, boomerang transition, lifetime and every other elapsed-time calculation; perform zero-distance canonical collision/impact normally, then remove the marker. Existing shots use unchanged dt. For a recognized newborn Sweep effect, its first `updateEffects` invocation uses per-object elapsed **zero**, still evaluates its due first pulse once, updates `pulseIndex`/hit map/next-pulse state normally, retains the full .3 second life, then removes the marker. Thus a 600 ms late update cannot expire a just-created Sweep before its first hit. Do not change the global delay-subtraction/continue rule for old effects or H's original delay. No `dt=0` for the entire array.

Children produced downstream by collision retain their existing source ordering; mark a child newborn only if that same frame's later step would otherwise consume pre-birth elapsed time. Tool Echo timers begin at actual release and their descendants do not set toolUse receipts or borrow the current hand. A physical Sweep is released when its actual effect has been created, so post-release melee may start before the normal later-in-frame first-pulse loop; H remains the special existing original-pulse gate. Tests must cover direct API draining as well as update-driven release, save/load before a newborn's first step, duplicate dt=0 calls, large/uneven dt, point-blank collision, and exactly one newborn Sweep pulse with full lifetime.
